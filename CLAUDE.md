# CLAUDE.md

## Project

A minimal shared-list app. Users create lists, add items, check them off. Lists are
shared with other users and every change propagates in real time to all devices
viewing the same list.

## Presets

There is **one item model**. Every item can carry every attribute: quantity,
recurrence, priority, notes, and candidate options with links.

A list owns a **quick-add field set** that controls only which fields the quick-add
form shows, so adding an item takes one or two taps instead of filling every
attribute. It never restricts what an item can hold: the item detail view always
exposes all attributes, on any list.

Presets are named starting points for that field set:

| Preset | Quick-add asks for |
|---|---|
| Household tasks | name, recurrence |
| Shopping list | name, quantity |
| Pending purchases | name, notes, options with links |
| Plain | name |

- Picking a preset copies its fields into the list. The list can then add or remove
  fields on its own without leaving the preset.
- The preset can be changed at any time. It rewrites the quick-add field set and
  leaves existing items untouched — no attribute is ever dropped from an item.
- An item in *Pending purchases* can repeat weekly: set it from the item detail
  view, since that quick-add form does not ask for recurrence.

Scope is added on request. Do not build a feature before it is asked for.

## List view

A list is one screen with two zones:

- **Open items** on top, unchecked. Default order is insertion order, and the user
  can reorder them by hand to raise what matters.
- **History** below, holding checked items in completion order.

Checking an item moves it to the history. It stays there as a record of that
occurrence and is never reused.

## Recurrence

A recurring item spawns a **new copy** in the open zone once its interval elapses
after completion. The completed occurrence remains in the history untouched, so the
history answers "did we buy it last time" for every cycle.

Copies are generated by the app, not by a person, and the list marks them so the
difference is visible at a glance. Each item records who created it, with automatic
copies attributed to no user, and keeps a reference to the occurrence it came from.

Due copies are materialized when the list is opened, so a list nobody opens grows no
items. Generation is idempotent: exactly one copy per completed occurrence, whoever
opens the list and however many devices open it at once. Copies chain, so an
uncompleted copy never piles up further copies.

## Outbound links

Item option URLs are stored **clean**, exactly as the source gave them. Affiliate
tags are appended when the user taps the link, never persisted on the row, so a
saved link stays valid, attribution lands inside the program's window, and
affiliation can be switched off without touching stored data.

Any marketplace search runs in a Supabase Edge Function: marketplace credentials
never reach the client. Affiliate links are disclosed as such in the UI.

## Stack

- **Frontend**: React + TypeScript + Vite, one plain stylesheet.
- **Backend**: Supabase (Postgres, Auth, Realtime, Row Level Security).
- **Hosting**: static build; Supabase is the only server.

No state library, no UI framework, no ORM. React state plus the Supabase client.

## Structure

```
src/
  lib/          # supabase client, shared helpers, types
  hooks/        # data hooks, one per concern (useSession, useLists, useItems)
  components/   # presentational components, one per file
  pages/        # routed screens
supabase/
  migrations/   # numbered SQL migrations, forward-only
```

## General rules

- Document the **stage, not the change**. Comments and docs describe the code as it
  is now, never as it was and never the edit that produced it. The documentation
  does not narrate its own history.
- Prefer short files with one identifiable responsibility over long files with many.
- Use the existing structure and conventions; prefer clarity over cleverness; reuse
  existing helpers instead of adding new ones.
- Ask for clarification only when the task is genuinely underspecified **or could
  change how shared data is written or who can read it**.

## Data flow

- Anything used by more than one component or hook lives in `src/lib/`, not
  duplicated at the call site. Types in `src/lib/types.ts`, Supabase client in
  `src/lib/supabase.ts`.
- Components render; hooks fetch, subscribe and mutate. A component does not call
  the Supabase client directly.
- Every table that holds user data has RLS enabled and a policy covering select,
  insert, update and delete. A new table without policies is an incomplete change.
- Policies decide which rows a user reaches; table privileges decide whether the
  role may touch the table at all. Both are required, and `authenticated` holds the
  privileges.
- Realtime subscriptions are scoped to the open list and torn down on unmount.
- Schema changes go in a new numbered migration under `supabase/migrations/`.
  Never edit an applied migration.
- Keys, URLs and env-dependent values come from `import.meta.env`, never hardcoded.

## Code style

- Comments always in **English**.
- Keep comments as short as possible, one line each. Comments explain what the code
  does, not why.
- `snake_case` for database identifiers, `camelCase` for TypeScript values and
  functions, `PascalCase` for components. Descriptive **English** names throughout.
- TypeScript strict; no `any`.

## UI

- Minimalist and intuitive: one primary action per screen, no nested menus, no
  settings the app can infer. If a control needs a tooltip to be understood, redesign it.
- Optimistic updates on item toggles, with the realtime event as the source of truth.

## Error handling

- Do **not** add redundant guards, null handling, or try/catch wrappers. Add a check
  only when it prevents a realistic failure or protects a critical step — network
  and auth calls qualify, local state transitions do not.
- Surface errors in the UI; never swallow them silently.

## Agents

- If a task shows up repeatedly (seeding data, applying migrations, generating types
  from the schema), turn it into a script under `scripts/` so it stays traceable and
  reproducible. The directory is created when the first script needs it.

## PROJECT_LOG.md maintenance

- Update it **only** when a change affects the data model, sharing or permission
  rules, the realtime mechanism, generated outputs, or project structure. Do **not**
  log formatting, comments, renames, or style/tooling fixes.
- Each entry: **Date, Summary, Files modified, Rationale**, kept to **3-8 lines**.
- When the file grows unwieldy, split older months into `PROJECT_LOG_archive.md`.
